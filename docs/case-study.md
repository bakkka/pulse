# Кейс: Pulse — SaaS-аналитика

## Контекст

Условный заказчик — SaaS-команда на 5–15 человек, которая уже продаёт подписку, но живёт в
таблице: MRR считают вручную, удержание не знают, воронку обсуждают по ощущениям.

**Боли:** цифры в разных местах, «мы вроде растём» вместо ответа на вопрос «почему», нет связи
между платежами и поведением продукта.

## Задача

Один экран, который отвечает на четыре вопроса:

1. Сколько мы зарабатываем и как меняется MRR?
2. Пользователи возвращаются?
3. Где теряются деньги в воронке?
4. Кто эти клиенты и что с ними происходит?

## Решение

**Пять аналитических экранов + операционка.**

- **Overview** — текущие метрики с динамикой, выручка по месяцам, движение MRR, распределение
  по тарифам, live-активность, топ клиентов по LTV.
- **Revenue** — переключатель 3/6/12 месяцев, история MRR, new / expansion / contraction / churn,
  net new MRR, последние счета.
- **Retention** — 12 когорт в heatmap и взвешенная кривая удержания.
- **Funnel** — 5 шагов, конверсия между шагами, самая большая просадка, среднее время до оплаты,
  источники.
- **Customers** — поиск, фильтры, сортировка, пагинация, CSV, карточка аккаунта со счетами,
  событиями и сменой тарифа.
- **Team** — owner / admin / viewer с реальными проверками на сервере.

## Ключевое решение: метрики считаются, а не рисуются

Самый частый грех портфолио дашбордов — статичные числа и картинки. Здесь наоборот:

| Метрика | Как считается |
| --- | --- |
| MRR на дату | последний счёт каждого живого клиента на эту дату |
| New / expansion / contraction | первый счёт и дельты к предыдущему счёту клиента |
| Churn MRR | последний счёт клиента, у которого `churnedAt` попал в период |
| NRR | `(start + expansion − contraction − churn) / start` |
| Когорты | доля когорты с событием `session` в месяце N |
| Воронка | уникальные клиенты по событиям внутри когорт выбранного окна |

Из этого следует важное: график движения MRR всегда сходится с текущим MRR. Если поменять счёт
в базе — поменяются все экраны.

## Модель данных

```
Customer ──< Invoice     деньги, история MRR, движение
Customer ──< Event       когорты, воронка, live
Customer >── Plan
Customer >── Member      владелец аккаунта
Member                   owner / admin / viewer
```

- 1 400 аккаунтов за 12 месяцев, 3 485 счетов, 13 594 события;
- детерминированный PRNG: одинаковые данные при каждом `db:seed`;
- статусы выведены из данных: `active`, `trialing`, `churned`, `lead` (не оплатил).

## UI-решения

- **Светлая тема + тёмный сайдбар** — намеренный контраст с тёмным Flowdesk.
- **Свои SVG-графики** вместо библиотеки: area, diverging bars, donut, heatmap, sparkline.
  Ноль зависимостей, полный контроль над пустыми состояниями.
- **Server Components для данных, client — только для hover и фильтров.** First Load JS ≈ 116 kB.
- **Тёмный акцент на цифрах:** табличные числа, компактные деньги (`$63.8k`), проценты без шума.

## RBAC

Роли проверяются в каждом server action, а не только прячутся в интерфейсе:

- viewer видит всё, но не имеет кнопок записи;
- admin меняет клиентов и настройки;
- owner управляет командой и пересборкой демо-данных;
- нельзя удалить последнего owner.

Демо: `owner@pulse.app` / `admin@pulse.app` / `viewer@pulse.app`, пароль `pulse`.

## Результат

- 7 экранов, 3 роли, CSV-экспорт;
- все метрики выводятся из 17 тыс. строк данных за миллисекунды на SQLite;
- демо открывается в один клик, данные воспроизводимы;
- код без chart-библиотек и UI-китов — проще поддерживать.

## Сроки

- схема + генератор данных: 1 день;
- метрики и графики: 1.5 дня;
- экраны и RBAC: 1.5 дня;
- полировка, тексты, скриншоты: 1 день.

≈ 5 рабочих дней.
